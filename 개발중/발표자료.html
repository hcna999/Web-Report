01 — 배경

왜 만들었나

한전은 배전선로에 들어가는 개폐기류를 납품받을 때 규격서에 정해진 시험을 거쳐 시험검사 성적서를 남깁니다. 이 문서가 합격 판정과 납품의 근거가 됩니다.

기존 방식
  • 품목마다 다른 엑셀 서식을 수기로 작성
  • 발취(표본) 수량을 규격서·절차서를 보며 손으로 계산
  • 판정 기준값을 사람이 대조 → 계산 착오·누락 위험
  • 작성분이 개인 PC에 흩어져 집계가 어려움
이 시스템이 하는 일
  • 규격을 고르면 시험항목·판정기준이 자동 구성
  • 로트수량·품질등급으로 발취수량 자동 산출
  • 측정값 입력 시 기준 대조 판정 자동화
  • 성적서를 PDF·엑셀·XML로 저장, 재편집 가능
최상위 기준은 구매규격(GS/ES 번호 규격서)입니다. 업무절차서는 그 하위 실무 지침이며, 둘이 어긋나면 구매규격을 따릅니다.

03 — 산출물

네 개의 도구

모두 독립적으로 열리는 단일 HTML 파일이며, 서로 파일(XML)로만 연결됩니다.

주 도구

성적서 작성 프로그램

규격 선택 → 발취 → 시험결과 입력 → 종합판정 → PDF·엑셀 저장까지 전 과정을 담당합니다.

분석

품질관리 대시보드

저장된 성적서(XML)를 한꺼번에 읽어 업체별·규격별 합격률과 불합격 항목을 집계합니다.

산출

발취점검 수량표 (단일규격)

규격 하나를 고르고 로트수량·품질등급을 넣으면 항목별 발취수량을 계산합니다.

인쇄

발취점검 수량표 (출력용)

전 규격의 항목별 발취수량을 한 장에 정리한 A3 대조표입니다.

04 — 아키텍처

서버도 빌드도 없는 단일 파일

전체 애플리케이션이 HTML 파일 하나에 들어 있습니다. 데이터·로직·화면·인쇄 서식이 모두 그 안에 있고, 빌드 도구나 프레임워크를 쓰지 않습니다.

이렇게 한 이유

사내 PC에 설치 권한이나 개발환경이 없어도, 파일을 열기만 하면 즉시 쓸 수 있어야 했습니다.

대가

파일 하나가 커지고(약 34만 자) 수정 시 충돌이 잦습니다. 규모가 더 커지면 분할이 필요합니다.

06 — 작업 흐름

검사자가 지나는 8단계

단계는 순서가 있는 실제 검사 절차를 그대로 따릅니다. 중간 시험 단계 구성은 규격마다 다릅니다.

발취수량 자동 산출

품질등급에 따라 배수가 붙습니다 — S·A 0.5배 / B 1배 / C 2배 / D 3배. 등급이 낮을수록 더 많이 뽑아 검사합니다.

중도 종료

불합격이 나오면 남은 시험을 진행하지 않고 즉시 결과 단계로 보냅니다. 실제 검사 규칙을 그대로 옮긴 동작입니다.

07 — 통신 구조

어디까지 나가고, 무엇이 남는가

서버 애플리케이션이 없기 때문에 외부와 오가는 통신은 네 갈래뿐입니다. 핵심은 시험 데이터 자체는 외부로 나가지 않는다는 점입니다.

시험 데이터는 ①②③④ 어디로도 자동 전송되지 않습니다. 검사자가 저장 버튼을 눌러 내려받은 파일이 유일한 보관 수단이므로, 파일을 잃으면 복구할 수 없습니다.

08 — 통신 상세

유일하게 데이터를 내보내는 경로

현장 검사자가 불편한 점을 남기면 구글 스프레드시트에 쌓입니다. 서버를 따로 두지 않으려고 Google Apps Script를 간이 수신 엔드포인트로 씁니다.

보내는 항목

timestamp · author · opinion · source

작성 시각, 작성자(이름 또는 회사명), 의견 내용, 작성 당시 보던 규격입니다.

설계상 한계

no-cors로 보내므로 브라우저가 응답을 읽지 못합니다. 전송 실패해도 화면에는 접수됐다고 표시될 수 있어, 실제 적재 여부는 시트에서 확인해야 합니다.

인증이 없는 공개 엔드포인트입니다. 주소를 아는 사람은 누구나 쓸 수 있으므로, 주소가 외부에 노출되면 새 배포로 교체해야 합니다.

09 — 산출물 형식

세 가지로 내보낸다

제출용

PDF

실제 성적서 서식(갑지·을지)을 그대로 옮긴 인쇄물입니다. 페이지마다 로고 워터마크와 쪽번호를 넣습니다.

가공용

XLSX

한전 실물 서식과 같은 병합 셀·테두리·머리글 음영을 넣어 생성합니다. 항목별 상세 시트가 분리됩니다.

재사용

XML

입력 내용 전체를 담은 원본입니다. 다시 불러와 이어서 작성하거나, 대시보드에서 집계합니다.

XML이 이 시스템의 실질적 데이터베이스입니다. 스키마는 kepco-qir-switchgear.v0.2이며, 작성 프로그램과 대시보드가 이 형식 하나로 연결됩니다. 서버 없이 도구를 잇는 방법이기도 합니다.

PDF는 html2pdf(jsPDF), 엑셀은 ExcelJS로 생성합니다. 두 라이브러리 모두 브라우저에서 직접 파일을 만듭니다.

10 — 배포 · 협업

배포는 파일을 올리는 일

빌드 단계가 없으므로 저장소에 올리면 곧 배포입니다.

배포 경로
  • 깃 저장소 main에 병합
  • GitHub Pages가 정적 파일 그대로 서빙
  • 접속 주소로 들어오면 성적서 작성 화면으로 바로 이동
  • 오프라인 배포가 필요하면 압축본을 그대로 전달
협업 방식
  • 기능별 브랜치에서 작업 후 병합
  • 배포본과 개발 자산 폴더를 분리해 관리
  • 인수인계 문서에 변경 이력·열린 이슈를 기록
단일 파일 구조의 대가는 협업에서 드러납니다. 두 사람이 같은 파일을 고치면 충돌이 잦으므로, 작업 전에 역할을 나누고 항상 최신 상태를 받은 뒤 시작해야 합니다.

11 — 보안

공개 웹에 올릴 때 생긴 문제

사내에서만 쓰던 파일을 공개 주소로 올리는 순간, 코드에 들어 있던 내용이 모두 외부에 보이게 됩니다. 구조 자체가 바뀌지 않아도 노출 범위가 달라집니다.

확인된 쟁점
  • 코드에 들어 있던 업체별 내부 평가 등급이 함께 공개됨
  • 의견 수집 엔드포인트 주소가 소스에 노출됨
  • 정적 호스팅은 접근 제어를 제공하지 않음
취한 조치
  • 내부 평가 등급 데이터를 코드에서 분리 — 검사자가 직접 선택하도록 변경
  • 등급을 참조하던 화면 문구도 함께 정정(잘못된 표기 방지)
  • 잔여 위험을 인수인계 문서에 명시적으로 기록
남은 한계 — 과거 이력에는 지운 내용이 그대로 남습니다. 또한 화면 코드에 비밀번호를 넣는 방식은 소스를 열면 보이므로 보호 수단이 되지 못합니다. 실제 접근 통제가 필요하면 인증을 제공하는 호스팅으로 옮겨야 합니다.

12 — 정리

무엇을 얻었고, 무엇이 남았나

달성
  • 규격 10종의 시험항목·판정기준을 데이터로 정리
  • 발취수량 산출과 판정 대조를 자동화
  • 성적서를 실물 서식 그대로 PDF·엑셀로 생성
  • 설치·서버 없이 주소만으로 사용 가능
남은 과제
  • 성적서 중앙 보관 — 확장 지점만 있고 미연결
  • 접근 통제가 필요한 경우 호스팅 이전
  • 단일 파일이 커지며 생기는 협업 충돌
  • 규격 개정 시 수량표·대시보드 수동 반영
핵심 설계 판단 — "서버를 두지 않는다"는 제약이 이 시스템의 형태를 거의 전부 결정했습니다. 덕분에 배포와 도입이 쉬웠지만, 데이터 중앙화·접근 통제·협업은 그 대가로 남았습니다.
